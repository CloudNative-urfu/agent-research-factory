## Why

DVARP needs isolated, evolving attack and defence with independent measurement. Today the
attacker is a chat-only model but its host shares a process/log with the defender; scenarios
can encode implementation knowledge and memory only spans attempts of one scenario.
The factory must manage incremental implementation through OpenSpec rather than claim
that new prompts alone implement process isolation or learning.

## What Changes

- Opt-in `development` configuration freezes an OpenSpec workflow and coevolution roadmap
  into new improvement assessments, leaving existing assessments and campaigns unchanged.
- Require a valid OpenSpec proposal, design, delta specs and task list linked to plan IDs.
- Preserve approved specifications in the successor and verify task evidence at report and critique.
- Carry OpenSpec history into later assessments. Package the CLI and validate this change in Nix.
- Enable the workflow for the declarative DVARP instance; activation remains the owner's action.

## Capabilities

### New Capabilities
- `spec-driven-revisions`: approved specs, task evidence and independent review across revisions.
- `coevolution-program`: staged requirements for isolated, provenance-controlled competitive learning.

### Modified Capabilities

None.

## Impact

Factory autopilot and deep_case validation, launcher dependencies, source-integrity records,
tests/docs and nix-dots DVARP configuration. No live campaigns are rewritten. This change
implements orchestration, not the experimental attacker/defender runtime itself.
