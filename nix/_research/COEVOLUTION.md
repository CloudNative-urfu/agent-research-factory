# DARP: программа состязательной эволюции, версия 1

## Контекст и цель
Продолжаем возвраты товаров и существующий прототип. Пользователь запросил эволюцию
атаки и защиты без доступа к внутренностям противника, с накоплением опыта обеими
сторонами. Это backlog разработки, НЕ описание уже работающей изоляции или обучения.
Сначала развиваются стратегии, промпты, память и версии кода. Обучение весов не требуется.
Качество — бизнес-инварианты, полезность легальных обращений и независимая оценка, а не
число атак или обязательный успех атакующего. Не ослабляй серверные правила.

## Известные исходные ограничения (перепроверь по текущему коду)
- В boundary-1 часть бизнес-правил была оставлена модели; сохраняй её только как legacy.
- Канал передаёт ограниченный Observation, но обе стороны размещены в одном Python
  процессе; ComponentWriter._emit ссылается на общий EventLog. Это не OS-изоляция.
- objective/drafts передаются атакующей модели без смысловой проверки происхождения.
- Обычный ответ агента может раскрыть внутренние сведения; нельзя смешивать такую атаку
  через разрешённый канал с непреднамеренным доступом к логам/файлам стенда.
- Память Attacker хранит только предыдущие попытки одного сценария и не переживает
  создание нового объекта. believed_success — вывод по тексту, не истинный исход по БД.
- Автор сценария знает код защиты; отдельная сессия той же модели не гарантирует слепоту.
- Исходная защищаемая сессия сбрасывается между попытками. Межраундовое обучение нужно
  вводить отдельно, не загрязняя независимую оценку и не меняя старый протокол молча.

## Последовательность зависимостей
За один проход выбирай 1–5 проверяемых задач OpenSpec. Начни с аудита текущего состояния
и обязательной основы. Выполненный пункт не делай заново; каждый остаток переноси явно.
Нельзя перескочить к заявлению о black-box эволюции, пока нижние уровни не проверены.

### A. Изолированная граница и наблюдаемость
1. Зафиксируй модель угроз, публичный контракт клиента и матрицу доступа:
   - атакующий: свой код/память, публичные правила/данные своего аккаунта, канал;
   - защитник: собственная реализация, данные и журналы, разрешённые обращения;
   - оценщик: приватные fixtures, oracle, полные журналы и скрытый held-out.
   Секреты/ключи остаются у брокера, а не в промптах и экспортируемом опыте.
2. Разные процессы с минимальными монтированиями и IPC по схеме. Одного subprocess,
   Python private-атрибута, разных каталогов или инструкции «не читать» недостаточно.
   Запрет доступа к чужим файлам/БД/логам, /proc чужого процесса, сокетам и лишней сети
   проверяется реальными отрицательными OS-тестами, включая ссылки и traversal.
   Используй уже доступный sandbox, где применимо, вместо дублирования инфраструктуры.
3. Аудируй точные payload запросов экспериментальным моделям (без секретов). Canary
   только синтетический. Смена скрытой политики/разметки при одинаковой разрешённой
   истории не должна менять вход атакующему. Нарушение границы исключает прогон из
   заявлений black-box. Исполнитель кода атакующего не получает весь снимок проекта.
4. Создание атак тоже изолируй: attack-only входы без исходников/критики защиты. Арбитр
   может читать обе стороны, но не писать тактики с привилегированным знанием в blind-набор.
   Для legacy сценариев записывай происхождение implementation-informed, не blind.
5. Обычные ответы, статусы клиентского API и разрешённое время ответа — наблюдения.
   Утечка системного промпта через ответ — отдельный измеряемый исход. Не скрывай её
   постобработкой ради «чистого» результата и не называй утечкой публичные правила магазина.

### B. Опыт без доступа к противнику
1. Раздельные постоянные хранилища attack/defence/judge; никаких общих summaries.
   Запись опыта: ID, роль, режим, версия противника, источник наблюдения, хеши, время,
   результат и статус подтверждения, происхождение (public/chat/research/privileged),
   train/dev/held-out split. Дедупликация, атомарность, восстановление после сбоя.
2. strict-black-box: атакующему только наблюдаемые клиентом исходы; при необходимости
   реализуй настоящий read-only статус заявки своего аккаунта. Слова модели — отдельное
   believed_success. Истинный oracle не становится скрытым бонусным API для атакующего.
3. research-feedback: разрешённый скаляр/категория от оценщика, явно привилегированный.
   Логи, оценки и опыт этого режима не смешиваются со strict. Фильтровать только текущий
   запрос недостаточно: память обучавшегося с privileged feedback также не является strict.
4. Защитник учится на своих наблюдениях и разрешённых прошлых инцидентах, не на приватной
   памяти атакующего и не на будущих тестах. Межраундовое обновление отдельно от диалога.
5. Retrieval и сжатие памяти сохраняют provenance; текст опыта — данные, не инструкции.
   Тесты отравления памяти, ошибочного успеха, непроверенного сообщения о согласовании,
   повреждения/подмены записи, бюджет контекста и перенос опыта после рестарта.

### C. Лига версий и независимая оценка
1. Замороженные версии attack/defence, памяти, правил и протокола на время раунда.
   Архивный manifest содержит хеши и родительские версии; обновление только между раундами.
2. Матрица новый атакующий × текущая и архивные защиты; новая защита × новые и архивные
   атакующие. Симметричные бюджеты, фиксируемое распределение до старта, одинаковые
   клиентские права. Прогоны без памяти — контроль пользы накопленного опыта.
3. Закрытый финальный набор у оценщика; разделение по семействам сценариев, не только
   перефразы. После раскрытия набор становится регрессией. Не допускать его в обучение
   через отчёты/критики/экспорт без смены статуса. Публикация раскрывает сценарии:
   после публикации следующая независимая оценка требует нового набора.
4. Метрики: исполненные нарушения, ущерб, легальный task success, ложные отказы,
   эскалации, задержки/стоимость, перенос на другие версии, забывание старых атак,
   разнообразие механизмов и неопределённость. Попытка и исполнение раздельны;
   timeout/обрезка не стирают уже совершённый вред и не считаются успехом защиты.
5. Критерий продвижения фиксируется до измерений; запрет «победы» отказом всем,
   подменой oracle или ослаблением серверного baseline. Нулевой эффект допустим.
   Остановка при отсутствии новой информации/ресурсов, а не бесконечная гонка ради гонки.
6. Один внешний Qwen в обеих ролях и малое n явно ограничивают переносимость выводов.
   Не объявляй разные сессии разными моделями. API-бюджеты фабрики остаются прежними;
   сначала offline/stub проверки механики, потом небольшой честный живой срез.

## Артефакты программы
В каждой новой оценке обновляй artifacts/coevolution-progress.md: пункт A/B/C →
implemented/partial/pending → код и доказательства → ближайшая зависимость. В начале
прохода фиксируй OpenSpec proposal/specs/design/tasks, после — результаты и остатки.
Критик независимо проверяет текущие пункты, включая отсутствие утечек в пути подготовки
атак, а не только в HTTP-запросе Qwen. Не признавай слабую изоляцию «упрощением»,
достаточным для заявленного strict-black-box: оставь этот режим неподтверждённым.
