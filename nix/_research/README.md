# Автономная исследовательская фабрика

`research-factory` управляет пятью реализациями с нуля, независимыми проверками,
памятью и выбором кандидата. Исполнители: `research-opencode` и `research-claude`.
Аспект подключён к `book`; версии инструментов закреплены `flake.lock`.

## 1. Установка

Из корня `nix-dots`:

```sh
nix build .#nixosConfigurations.book.config.system.build.toplevel --show-trace
sudo nixos-rebuild switch --flake .#book
```

Новые файлы должны быть в индексе Git для `import-tree`. Коммиты создаёт пользователь.
Авторизация обоих исполнителей выполняется отдельно от повседневных профилей:

```sh
research-opencode
research-claude
```

В OpenCode использовать `/connect` и `/models`. Claude Code запускается с Opus;
войти в нужный аккаунт. Автоматической ротации аккаунтов нет. API-ключи можно
передавать через поддерживаемое провайдером окружение без записи в Nix store.

## 2. Создание кампании

```sh
research-factory init ~/.local/share/research-campaigns/defense \
  --brief /absolute/path/agent-defense-and-continuity.md \
  --config /absolute/path/campaign.example.json
```

Команда копирует постановку и создаёт `campaign.json`. В нём указать настоящий
идентификатор модели исследователя, выбранной в OpenCode, в `researcher.model`.
Пример структуры (значение `PROVIDER/MODEL` необходимо заменить):

```json
{
  "cycles": 5,
  "attempts_per_stage": 2,
  "timeout_seconds": 14400,
  "verify_timeout_seconds": 3600,
  "max_log_bytes": 67108864,
  "max_snapshot_bytes": 2147483648,
  "researcher": {"backend": "opencode", "model": "PROVIDER/MODEL"},
  "critic": {"backend": "claude", "model": "opus"}
}
```

Обе роли поддерживают `opencode` и `claude`. Критик всегда получает отдельную сессию.
Время и объём архива — стартовые операционные границы, их следует уточнить после
пилота. Это не лимит токенов провайдера и не точный денежный бюджет. Затраты,
сообщённые исполнителями, сохраняются в квитанциях; прерванный процесс может не
сообщить полный расход. Сводить стоимость подписки к фиктивной цене токена нельзя.

По умолчанию используется локальный OpenRouter-прокси. Скопируй установленный
`~/.config/agent-research/openrouter.example.env` в `openrouter.env` в той же папке
с правами 600, подставь ключ и запусти `systemctl --user start research-llm-proxy`.
Проверка реального API: `research-llm-proxy --check`. Только процесс прокси получает
`OPENROUTER_API_KEY`; в окружение фабрики этот ключ не импортировать.
Пошаговая инструкция находится в корневом `RESEARCH-PIPELINE.md`.

Для другого API можно предоставить в окружении:

- `RESEARCH_LLM_BASE_URL` — URL с `/v1`, без секретов в URL;
- `RESEARCH_LLM_MODEL` — фактический API model ID;
- `RESEARCH_LLM_API_KEY` — если сервер требует аутентификацию.

Публичные `base_url`, `model` и объявленный `context` также можно задать в объекте
`experiment` файла кампании. Переменные окружения имеют приоритет; секреты туда
не входят. Корневой `campaign.example.json` уже содержит предоставленный адрес.

Экспериментальная модель — отдельный ресурс, а не модель исследователя. Контроллер не
читает `.env` или файлы ключей. Значения ключей в конфигурацию кампании не добавлять.

## 3. Проверка и запуск

```sh
research-factory doctor ~/.local/share/research-campaigns/defense
research-factory doctor ~/.local/share/research-campaigns/defense --live
research-factory run ~/.local/share/research-campaigns/defense
research-factory status ~/.local/share/research-campaigns/defense
```

Обычный `doctor` проверяет инструменты и изоляцию. `--live` дополнительно выполняет
реальные MCP-вызовы, запрос экспериментальной модели и короткий вызов инструмента каждой
моделью-исполнителем. Это расходует лимиты. `run` автоматически делает живую проверку
перед продолжением незавершённой кампании; завершённую кампанию повторно не запускает.
Подробности доступны в `doctor.json` и каталоге `doctor/`.

Для фонового выполнения после предоставления переменных окружения:

```sh
systemctl --user start research-campaign@defense
systemctl --user status research-campaign@defense
journalctl --user -u research-campaign@defense -f
```

При переопределении API импортировать только установленные переменные через
`systemctl --user import-environment ИМЯ_ПЕРЕМЕННОЙ`; при API-авторизации исполнителей
аналогично импортировать нужные переменные провайдера. Unit ищет кампании именно в
`~/.local/share/research-campaigns/<имя>`. После выхода из пользовательской сессии
работа user service зависит от настроек login manager/linger.

## 4. Стадии и контракты

| Стадия | Обязательный результат |
| --- | --- |
| research | `artifacts/hypotheses.md`, `sources.json`: источники, статус проверки, гипотезы |
| plan | `protocol.json`: hypothesis, baselines, metrics, falsification, split_policy, budget |
| build | MVP и `submission.json`: `verify_command` как массив аргументов |
| experiment | `results.json`: measurements и evidence — пути к исходным данным |
| report | `report.md`, `memory.json`: facts, failures, unknowns, next |
| verify | Контроллер запускает verify_command в чистой копии, сохраняет код возврата и лог |
| review | Независимая сессия критика; `artifacts/review.json` и доказательства |
| confirm | После всех циклов — новая независимая проверка кандидата на новых случаях |

Команда `verify_command` должна устанавливать закреплённые зависимости и проверять
существенное поведение. `.venv`, `node_modules`, кеши и исходники `.git` не попадают
в архив. Все стадии проходят в свежих сессиях, но внутри одного цикла рабочие файлы
сохраняются. Повтор после сбоя продолжает тот же этап, а не начинает новый цикл.

Критик сообщает verdict `accept/revise/pivot/blocked`, score 0..4, отдельные булевы
gates `reproducible`, `hypothesis_supported`, `useful`, `relevant`, `valid_evaluation`,
список issues с severity/evidence/fix, evidence, summary, next, publication_ready.
Нужны непустые существующие файлы доказательств. Приёмка невозможна при ложном
обязательном gate, blocking-замечании или провале внешней команды проверки.

Кандидаты, принятые в review, ранжируются по оценке критика; при равенстве — по номеру
цикла. Затем независимо подтверждаются по очереди до первого успешного кандидата.
Это эвристика отбора для MVP, а не доказательство статистического превосходства.
Готовность статьи сообщается отдельно. Рукопись и препринт не публикуются автоматически.

## 5. Память, контроль и восстановление

Каждый цикл начинается в пустом `cycles/NN/work`. Память предыдущих реализаций
передаётся как `handoff.json`: факты, провалы, неизвестные и критика.
`prior-evidence/` содержит подробные протоколы, обзоры, отчёты и текстовые/табличные
данные по ссылкам. Исходники прежнего MVP туда не копируются. Плагин OpenCode
автоматически добавляет handoff в новый запрос; Claude получает явную инструкцию
прочитать этот же файл. Длинная история чата не используется как источник истины.

Контроллер использует атомарные записи состояния, эксклюзивную блокировку,
ограниченное число попыток и тайм-ауты. После этапов остаются запросы, логи и
квитанции `logs/*`; после report — снимок с SHA-256-манифестом.
Итог: `FINAL.md`, `selection.json`, принятый `cycles/NN/snapshot` и подтверждение.
Архивы не удаляются автоматически. Ключи известных переменных маскируются в логах.

Исполнители запускаются через bubblewrap: запись разрешена в своём рабочем каталоге,
временном пространстве и отдельных каталогах профилей. Каталог кампании скрыт,
поэтому исполнитель не может менять состояние контроллера и старые снимки.
Постановка, переданная память, замороженный протокол и кандидат для критика
монтируются только для чтения. Критик может сделать копию кандидата для повторного
запуска и обязан сохранить новые измерения отдельно.

Это изоляция записи и состояния кампании, не полная секретность хоста: прочие
доступные пользователю файлы остаются read-only, сеть доступна. Инструкции запрещают
читать секреты через shell. Профили авторизации общие между стадиями данного
исполнителя; независимость критика — отдельный процесс/контекст и проверка
артефактов, а не доказанная независимость ошибок моделей.

Остановка:

```sh
systemctl --user stop research-campaign@defense
```

После сбоя обычный `run` продолжает сохранённую стадию. При исчерпании попыток
контроллер возвращает код 2 и сохраняет причину. После пополнения ключей или
исправления ресурса:

```sh
research-factory run ~/.local/share/research-campaigns/defense --retry
```

`--retry` сбрасывает счётчики попыток, сохраняя реализации и журналы. Unit
перезапускается после аварийного выхода, но не зацикливает блокировку с кодом 2.
Для новой кампании с новым бюджетом создать новую директорию. Исчерпанный бюджет
без принятого кандидата означает `exhausted`, а не успех.

## 6. Проверки разработки

```sh
python3 -m unittest discover -s modules/aspects/agent-harness/_research -p 'test_*.py'
python3 modules/aspects/agent-harness/_research/mcp_probe.py
```

Для полного набора нужны `opencode`, `claude`, `bwrap` в PATH. Если Claude доступен
по другому пути, задать `RESEARCH_TEST_CLAUDE`. Тесты транспортов запускают настоящие
CLI с синтетическими HTTP-моделями и настоящими shell-вызовами. OpenCode-тест
проводит два цикла и финальную проверку внутри bubblewrap. Это проверка механики,
не измерение качества реальных моделей. Проверка живых ключей — `doctor --live`.

OpenCode V2 может вернуть пустой реестр через `debug agents` до активации рабочего
контекста; пригодность профиля проверяется реальным `run`, а не только списком.
Launcher через официальный CLI отключает общий сервис только исследовательского
профиля: команды используют приватные серверы и не конфликтуют с портом обычного
OpenCode. Это также исключает сохранение старого пути конфигурации в долгоживущем сервисе.
